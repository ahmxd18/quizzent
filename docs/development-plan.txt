QUIZZENT — ORDERED DEVELOPMENT PLAN

Goal: a clear, reliable portfolio project built one small step at a time.
Status: [x] completed, [ ] pending. Update this file as work progresses.

WORKING RULES
- Keep main stable. Develop on feature branches and merge through pull requests.
- Make one focused commit per reviewable change. Do not mix unrelated features.
- Check each change before committing; push small completed commits.
- Build a feature's backend and frontend together once the foundations exist.
- Explain unfamiliar TypeScript, PostgreSQL, and Socket.IO briefly as they appear.
- Use short, useful comments and named colour tokens. Reuse components when useful.
- Add dependencies when needed, not for hypothetical future features.
- Run targeted checks with each feature; do not postpone correctness to the end.

10. [ ] Live lobby and readiness
    Add Socket.IO only now; authenticate guest/organiser subscriptions.
    Add ready/unready, distinct ready counts, and short presence leases.
    A presence lease means a competitor counts only while recently connected.
    Check: two tabs count once, disconnect expiry, reconnect, and unauthorised rooms.

11. [ ] Automatic start and five-second warning
    Persist lobby countdown deadlines; start only after countdown and minimum-ready rules.
    When eligible, run a five-second warning before atomic roster admission.
    Proposed: if ready count falls below minimum, wait and restart the five seconds later.
    Confirm this behaviour when implementing it; it is currently a proposed default.
    Close late admission and show the committed state to all clients.
    Check: threshold races, disconnect during warning, repeated start triggers.

12. [ ] Assigned questions and immutable answer submission
    Persist an independent question/option permutation for every admitted guest.
    Return only the current question; keep keys and other submissions private.
    Save one answer and advance in one transaction (an all-or-nothing database change).
    Use request IDs so retrying an accepted answer cannot score twice.
    Build the question screen and submission/loading states.
    Check: conflicting answers, sequence bypass, retries, and refresh after submission.
    Split assignment, submission engine, and question UI into separate commits.

13. [ ] Authoritative timing, timeout progression, and reconnection
    Use the same organiser-configured limit for each question, default 10 seconds.
    Save server issue times and deadlines; browser timers are display only.
    Proposed: individual disconnections do not pause timers; timeouts receive full time.
    Confirm these defaults when implementing them.
    Restore the same attempt and reconcile missed deadlines without resetting time.
    Check: exact deadline, answer versus timeout, offline expiry, and lost updates.

14. [ ] Final results and organiser progress
    Rank by correct answers descending, then total answer time ascending.
    Proposed: share ranks for exact ties and release correctness after completion.
    Recalculate final results from saved resolutions before publishing them.
    Add a simple organiser progress view and final competitor leaderboard.
    Check: ties, unanswered questions, simultaneous finishes, and private data visibility.

15. [ ] Cancellation and server outage handling
    Add explicit cancellation with a reason and a clear cancelled screen.
    On server restart, cancel affected active competitions rather than resuming them.
    During loss of contact, show a connection warning; confirm cancellation on recovery.
    Check: restart mid-competition, cancellation versus answer, no invalid final results.

16. [ ] Minimal superadmin controls
