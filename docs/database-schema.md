# First database migration

`server/migrations/0001_accounts-and-sessions.sql` creates the first application tables. Signup and login endpoints are not implemented yet.

## Apply changes

Start Postgres.app, configure `server/.env`, and run from the project folder:

```sh
npm run db:migrate
```

`node-pg-migrate` runs pending SQL files in order and records them in its `pgmigrations` table. Running the command again leaves already-applied migrations alone. Migration writes are transactional, so a failed migration does not leave half its changes applied.

Keep applied migrations unchanged. Add `0002_...sql` for the next structure change. Do not run the SQL file directly in psql, because that bypasses the migration history.

The tool is a development dependency. Deployment will need an explicit migration step with this dependency available before starting the new backend version.

## Tables

### users

Registered organiser and superadmin accounts live here. Guest competitors will have their own identity model later; they do not need a registered account.

| Field | Purpose |
| --- | --- |
| `id` | Random UUID generated by PostgreSQL; identifies one account |
| `display_name` | Trimmed name, 1–80 characters |
| `email` | Trimmed email, unique regardless of capitalisation |
| `password_hash` | Hash produced by the future authentication code, never a raw password |
| `role` | Defaults to `organiser`; only `organiser` and `superadmin` are allowed |
| `status` | `active` or `suspended` |
| `created_at` | Creation time as a timestamp with time zone |

`PRIMARY KEY` makes each ID unique and required. `NOT NULL` means a field cannot be missing. `CHECK` rejects values outside a rule. The unique index on `lower(email)` prevents both `alex@example.com` and `Alex@example.com` from becoming separate accounts, even when inserts overlap.

Email format validation and secure password hashing still belong in the upcoming signup implementation. A nonempty database field alone cannot prove that an email is deliverable or that a password was hashed correctly.

The role default is not a permission system. Public signup must explicitly create an organiser and ignore/reject client-supplied privileged roles. Account ownership and route permissions also need backend checks.

### user_sessions

Each row represents one registered account's login session. Multiple sessions per account are allowed; the one-active-room rule will be enforced on competitions, not login sessions.

| Field | Purpose |
| --- | --- |
| `id` | Random session record ID |
| `user_id` | Account this session belongs to |
| `token_hash` | Unique 64-character hexadecimal SHA-256 hash of a random session token |
| `created_at` | Session creation time |
| `expires_at` | Expiry time, which must be after creation |

The browser will receive a random token in a protected cookie. The database will store only its hash. This is separate from password hashing: passwords need a deliberately slow password-hashing algorithm.

`REFERENCES users(id)` is a foreign key: a session cannot refer to an account that does not exist. `ON DELETE CASCADE` removes that account's sessions when the account is deleted. Logout can delete a session; authentication must check expiry and account status on use. Merely having an expired row in the database must never keep someone signed in.

Indexes on `user_id` and `expires_at` support account session lookup and eventual expiry cleanup.

## Verify the migration

```sh
npm run test:db
```

These integration tests use a real PostgreSQL connection and create a random, isolated schema (a namespace for tables). They check defaults, case-insensitive email uniqueness, account constraints, session links, token uniqueness, expiry ordering, and account/session deletion. They also apply, rerun, roll back, and reapply the migration. The temporary schema is removed afterward; public application records are untouched.

The migration's `Down Migration` section drops accounts and sessions. It exists for disposable-schema testing and must not be used casually on a database containing real data.

The migration tool's `glob` dependency is overridden to a patched compatible version to avoid advisories in the version it requests. Migration loading and execution are covered by the integration tests. Revisit the override when updating the tool.

References: [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html), and [node-pg-migrate](https://salsita.github.io/node-pg-migrate/getting-started).
